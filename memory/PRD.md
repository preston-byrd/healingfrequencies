# PRD — Healing Frequencies

## Original problem statement
"Can you create healing frequencies"

## User choices (from initial ask_human)
- Both: preset Solfeggio + custom frequency generator
- Features: timer/session length, background visuals, ambient nature sounds layer mixed with tones, save favorite sessions, breathwork guide synced to tones
- Pure Web Audio API (no audio files)
- Design vibe: blend of calm/minimal, cosmic/mystical, nature/earthy
- Auth required (JWT email + password)

## Architecture
- **Backend:** FastAPI + Motor (async MongoDB). JWT auth in httpOnly cookies (SameSite=None, Secure) with Authorization Bearer fallback.
- **Frontend:** React 19 (CRA + craco). Tailwind CSS, lucide-react icons. Canvas-based visualizer.
- **Audio:** Web Audio API singleton engine. Oscillator for tone (sine/triangle/square/sawtooth) + optional binaural offset via channel-split. Three ambient layers (rain/ocean/forest) generated from pink-ish noise + biquad filters (low-pass for ocean with LFO, high-pass for rain, band-pass for forest).
- **DB collections:** `users` (id, email, name, password_hash, role, created_at), `sessions` (id, user_id, name, frequency, waveform, binaural, duration_minutes, ambient, breathwork, created_at).

## User personas
- Wellness seeker who opens the app for a quick guided sound-bath / meditation session.
- Practitioner / power user who composes custom mixes (frequency + binaural + ambient layers) and saves them.

## Core requirements (static)
- Email/password auth (register, login, logout, /me)
- Solfeggio preset grid (174, 285, 396, 417, 432, 528, 639, 741, 852, 963 Hz)
- Custom frequency slider 20–1200 Hz with waveform selector
- Binaural offset 0–40 Hz
- Tone volume control
- Ambient mixer (rain / ocean / forest) with independent volume
- Session timer 1–60 min with on-screen countdown
- Animated visualizer (canvas; pulses with frequency + play state)
- Breathwork guide overlay (4-4-6 cycle, phase label)
- Saved sessions (CRUD scoped to logged-in user) with one-click load

- **Isochronic gate click-artifact fix (iter 45)** (Feb 2026): fixed the "unwanted pulsating isochronic-like sound at screen lock" that persisted after iter43's haptic fix.
  - **Root cause** — the isochronic entrainment gate was implemented with a hard square-wave LFO modulating `gateGain.gain` between 0 and 1 (`_spawnIsochronicLFO` at audioEngine.js L555). The instantaneous 0↔1 transitions created audible click artifacts at each pulse edge. Under normal foreground playback these clicks were partially masked by the tone body and ambient environment. Under **screen-lock playback**, however, the audio pipeline shifts to the MediaStream → hidden `<audio>` element route, which buffers differently and reveals — even amplifies — the sharp-edged clicks. The user perceived this as an "unwanted pulsating sound" that only tap-Stop → tap-Play from the lock screen would clear (briefly), because the fresh audio graph hasn't yet accumulated scheduled gain values.
  - **Fix** — inserted a `BiquadFilterNode` (lowpass, 120 Hz cutoff, Q=0.5) between the square LFO and the scale/offset chain in `_spawnIsochronicLFO`. This softens each square-wave edge from 0 ms → ~3–5 ms transition — inaudible as a click, still perceptually a discrete pulse for entrainment. `_killIsochronicLFO` was updated to also disconnect the new `isoSmoother` node for clean teardown.
  - **Why this addresses the lock-screen case specifically** — a fresh audio graph (post tap-Stop / tap-Play) does not "fix" anything at the graph level; what it does is momentarily reset the buffer-alignment between the AudioContext and the MediaStream sink. As buffering realigns, the hard-square clicks resurface. Softening the edges of the underlying signal removes the mechanism entirely: no click content → nothing for the buffering pipeline to amplify.

- **Lock-screen audio artifact fix (iter 43)** (Feb 2026): eliminated the "pulsating vibration-like noise" users reported after the phone's screen lock kicked in.
  - **Root cause** — `hapticEngine._cycleFor('frequency', …)` mapped the binaural / isochronic rate 1:1 onto `navigator.vibrate` calls, previously capped at **30 Hz**. Human touch fuses discrete vibrations above ~4 Hz into a continuous mechanical buzz, and that buzz rattles the phone chassis on hard surfaces — an acoustic artifact that bleeds into the speaker as the reported "pulsating" noise, most audible when the screen is off and the phone is set down.
  - **Fix #1 — rate cap** — the frequency pattern now folds any rate >4 Hz into its sub-harmonic until it lands in **0.5–4 Hz** (integer bisection). The user still feels a rhythm coupled to the entrainment rate — just at a cadence the motor can render discretely instead of buzzing continuously.

- **Audio robustness hardening (Feb 2026)**: Three targeted fixes closing edge cases in the audio engine.
  - **Switch-frequency-while-playing resume path** — `setFrequency(hz)` used to schedule `setTargetAtTime` calls unconditionally against `ctx.currentTime`. - **HF-037 Android audio optimizations (Feb 2026)**: Users on mid-range Android devices reported distorted, choppy audio while iOS + desktop were fine. Root cause was a stack of Android-specific issues in the Web Audio graph: on-the-fly sample-rate resampling (96 kHz → 48 kHz mixer), unity-gain sums clipping the OS driver, and eight noise BufferSources + four LFOs pre-built for ambient layers that ran forever burning ~5-8% of the audio-thread budget even at gain=0.
  - **UA detection** (`audioEngine.js`): new module-level constants `_IS_ANDROID` (RegExp on `navigator.userAgent`), `_MASTER_CEILING` (0.85 on Android, 1.0 elsewhere), `_SCHEDULE_LEAD_MS` (120 ms on Android, 50 ms elsewhere). All three are read-only at ctx-creation time so there's no per-frame branching cost.
  - **Sample-rate alignment**: `_ensureCtx()` now requests `[48000, 44100]` on Android (matches hardware mixer, zero resampling) vs `[96000, 48000]` on desktop/iOS. Eliminates the largest source of distortion on Android — the browser used to accept 96 kHz then downsample every frame.
  - **Buffer / scheduling headroom**: `startAt = ctx.currentTime + _SCHEDULE_LEAD_MS/1000` — Android gets 120 ms lead-time (up from 50 ms) so the audio thread has enough room to pack the render buffer before the deadline. Same knob also applied to `_rampMasterOnResume`.
  - **Master gain ceiling**: on Android, `master.gain` holds at 0.85 (~−1.4 dB) instead of unity. Every setter that used to snap the bus back to `1` now uses `_MASTER_CEILING`, including the smart-fade recovery, the resume-fade-in, and the initial start-of-session reset. Gives the OS mixer clip-headroom for `tone + ambient + isochronic` sums without audibly attenuating the mix.
  - **Lazy ambient GC**: `_prebuildAllAmbient()` short-circuits on Android — the 8 ambient layers are now built on demand via the existing `setAmbient` fallback path. Idle Android CPU drops significantly; sample-alignment is preserved because the first-touched layer sets the reference `ctx.currentTime` for that session.
  - **Debug hooks**: `getState()` now returns `{androidMode, masterCeiling, scheduleLeadMs}` alongside `sampleRate` so the fidelity panel + support triage can see which platform-tuning path a given session is on.
  - **Files** — `frontend/src/lib/audioEngine.js` (~+30 LOC of constants + 6 targeted call-site rewrites; zero behavioural change on desktop/iOS).
  - **Verified** — Frontend compiled with only pre-existing lint warnings. Static grep confirms every `master.gain` write and every scheduled `startAt` respects the new constants. Desktop/iOS path is byte-equivalent to pre-HF-037 (constants collapse to `_MASTER_CEILING=1.0`, `_SCHEDULE_LEAD_MS=50`, prebuild runs eagerly, sample-rate attempts unchanged).
  - **NOTE** — Fix lives in **preview**. Redeploy required to reach solarisound.com. Android users should redeploy + hard-refresh to pick up the tuned engine.
- **HF-038 Android audio startup hardening (Feb 2026)**: Follow-up to HF-037 addressing the last three known distortion vectors on Android — resampling drift, startup-window clipping, and resume-ramp pops.
  - **Force hardware sample-rate match** (`audioEngine.js::_probeHardwareSampleRate`): new module-level helper creates a throwaway `AudioContext()` with no options, reads its resolved `sampleRate` (which is always the OS mixer's native rate), closes it, then feeds that exact value into the real context via `new AudioContext({ sampleRate: hw })`. On Android the attempts list becomes `[hw, 48000, 44100]` — the browser never resamples on-the-fly, eliminating the largest remaining CPU spike. Desktop/iOS untouched. Probed value is stashed on `this._hardwareSampleRate` and surfaced via `getState()` for debug.
  - **Startup gain floor** (`_MASTER_STARTUP_FLOOR = 0.65` on Android, 1.0 elsewhere): master bus now opens at ~−3.7 dB during the fragile first ~250 ms of playback (oscillator schedule + noise buffer alloc + first render quantum all coincide inside a single render window on Android). Every write that used to snap the bus back to unity honours this floor at ctx-create time.
  - **Post-create settle ramp** (`_settleMasterAfterCreate`): after ctx creation, waits `_RESUME_SETTLE_MS` (30 ms on Android) so the audio clock has committed at least one render quantum, THEN linearly ramps master from the startup floor (0.65) up to the ceiling (0.85) over 250 ms. Bails out if a later `start()` has already snapped master higher — no fight with in-flight schedules.
  - **Clock-synchronized resume fade-in** (`_rampMasterOnResume`): on Android the 50 ms resume fade is now scheduled AFTER the settle window elapses (`setTimeout(schedule, _RESUME_SETTLE_MS)`). Fixes the initial "pop / stutter" users heard right after screen-unlock because the ramp was starting mid-burst while ctx.state was still flipping to 'running'. Desktop/iOS path unchanged (`_RESUME_SETTLE_MS = 0` → synchronous scheduling).
  - **Files** — `frontend/src/lib/audioEngine.js` (~+70 LOC: probe helper, startup floor const, settle ramp, resume defer, expanded `getState`).
  - **Verified** — Frontend compiled with only pre-existing warnings. `grep` confirms every master-write path respects the correct constant (startup uses `_MASTER_STARTUP_FLOOR`, everything else uses `_MASTER_CEILING`). Desktop/iOS behaviour is byte-equivalent (`_MASTER_STARTUP_FLOOR=1.0`, `_RESUME_SETTLE_MS=0`, hardware probe is skipped).
  - **NOTE** — Fix lives in **preview**. Redeploy required for Android users on solarisound.com to hear the difference; a hard-refresh after redeploy will kick the tuned engine into their session.
